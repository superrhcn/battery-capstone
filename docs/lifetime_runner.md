# 장기 수명 실행기: 범위와 재개 조건

기존 물리 모델은 바꾸지 않고 장기 운전·진단·중단·저장 제어를 별도 모듈로 추가하였다. 기존 `battery.py`, `run_100efc.py`, 세 물리 설정 JSON은 실행 커밋 `777153d2f8b695fa12510dcd50ac5d3ec16249c8`의 바이트와 동일하다. 이 문서는 실행기 구현을 설명하며 SOH 80% 도달 실험의 완료 기록은 아니다.

## 입력과 출력

| 구분 | 항목 | 기본값 또는 처리 |
| --- | --- | --- |
| 셀 | `--cell` | 4 |
| 충전 CC 전류 | `--current` | 3.2 A, 궤적 중 고정 |
| 공간 격자 | `--mesh-scale` | ×4 |
| 사용량 상한 | `--efc` | 3,000 EFC |
| 진단 종료 SOH | `--eol-soh` | 80% |
| 실행시간 상한 | `--max-wall-s` | 누적 72,000 s = 20 h |
| 100 EFC 이후 기준시험 간격 | `--rpt-every-efc` | 10 EFC, 사용자 확정 |
| 프로세스 RAM 상한 | `--max-memory-gib` | 24 GiB |
| 시스템 여유 RAM 하한 | `--min-free-memory-gib` | 2 GiB, Linux에서 확인 |
| 디스크 여유 하한 | `--min-free-disk-gib` | 2 GiB |
| 원본 import | `--import-100efc-dir` | 완료된 기존 첫-100-EFC 결과 폴더, 읽기 전용 |
| 장기 결과 | `--output-dir` | 원본과 겹치지 않는 새 전용 폴더 |
| 같은 장기 실험 재개 | `--resume` | 장기 체크포인트의 소스·설정·패키지 식별값이 같을 때만 허용 |

진단 기본 시점은 0, 5, 10, 20, …, 100 EFC 이후 110, 120, …, 3,000 EFC이다. 총 302개 시점이다. 이미 원본에서 측정한 시점은 재측정하지 않는다. 100 EFC 이후 10 EFC 간격은 사용자가 확정한 조건이다. `--rpt-every-efc`로 100 EFC 이하의 양수 간격을 명시할 수 있다.

`elapsed_wall_s`는 기존 원본 실행시간과 이후 재개 실행시간을 합친 누적값이다. 원본 100 EFC가 약 40분 걸렸다면 20시간 상한에서 남은 연장 계산 예산은 약 19시간 20분이다. 일시 중지 후에도 시간 장부를 초기화하지 않는다. 누적 실행시간 감시기는 15초의 여유 뒤에도 응답이 없으면 자식 프로세스를 종료한다. 부모 프로세스가 SIGTERM·SIGINT를 받으면 자식에 종료를 전달하고 최대 60초 동안 안전 저장·종료를 기다린다. 자식 종료를 확인한 뒤에만 자기 잠금 파일을 정리하며, 응답이 없는 자식은 강제 종료하고 회수한다. 이 신호 경로는 `lifetime_supervision.py`에 분리하였다.

환경변수 `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS`는 별도 값이 없으면 각각 1로 설정한다. AWS 인증정보·메일 비밀번호는 실행기에 넣지 않는다. 컴퓨터·채팅 종료와 무관한 실행과 메일·인스턴스 중지는 별도의 클라우드 실행 스크립트가 맡는다.

## 원본 상태를 이어가는 방법

기존 100 EFC 실행기는 방전 중 목표 EFC에 도달하면 멈추고 장부의 `stage`를 `STOPPED`로 기록한다. 같은 계산 함수를 다시 호출하면 충전부터 시작하므로, 단순히 목표값만 늘려서는 같은 운전을 이어갈 수 없다.

새 실행기는 마지막 주기의 `discharge_end=efc_target` 기록을 검증하고 재개 위치를 `DISCHARGE`로 복원한다. Q0, 누적 방전 Ah, 전극 농도, SEI·도금·기공률 상태는 원본 체크포인트에서 가져온다. 먼저 남은 방전을 수행하고 SOC 20%에 도달하면 휴지한 뒤 다음 충전을 시작한다. 이후 장기 체크포인트에는 운전 단계와 미완 주기의 문맥도 함께 저장한다.

원본 import 전에는 다음을 확인한다.

1. 원본의 모델·설정·실행기 SHA-256이 고정한 기존 커밋의 5개 파일과 일치하는지 확인한다.
2. 셀·전류·격자·솔버 허용오차·패키지 버전·Python 버전을 비교한다. 일치하지 않으면 거부한다.
3. 요약 JSON과 체크포인트의 장부·식별값, 종료 상태와 도달 EFC를 대조한다.
4. 체크포인트·요약·진단·모든 원본 Parquet를 읽어 SHA-256을 기록하고 import 전후의 값이 같은지 확인한다.

`pickle` 체크포인트는 실행 가능한 파일 형식이다. 본인이 만든 신뢰할 수 있는 실험 결과에만 사용한다. 버전 불일치를 무시하는 옵션은 제공하지 않는다. 새 출력 폴더의 `lineage.json`은 원본 경로·파일 해시·원본 실행시간을 보존한다.

## 중단 판정

| `outcome.json` 상태 | 의미 |
| --- | --- |
| `eol_observed` | 기준시험에서 처음 SOH 80% 이하를 관측 |
| `max_efc_censored` | 최대 EFC까지 운전했지만 수명 종료를 관측하지 못함 |
| `wall_time_censored` | 누적 실행시간 상한으로 중단 |
| `resource_limit_censored:…` | RAM·디스크 여유 조건 때문에 중단 |
| `interrupted_censored` | 종료 신호를 받고 유효 상태를 저장한 뒤 중단 |
| `operating_condition_not_met:…` | 조기 저전압 종료·CV 정체 등으로 정한 운전을 유지하지 못함 |
| `failed` | 예외·수치 조건 위반. `FAILED.json`에 원인을 기록 |
| `paused_verified` | 짧은 검증에서 지정한 구간 수 뒤 저장하고 중지 |

SOH 80%가 예를 들어 200 EFC에서는 넘고 210 EFC에서 이하로 측정되면 실제 통과 시점은 `(200, 210] EFC` 구간에 있다. 210 EFC는 최초 관측 시점이며 정확한 수명 종료 시점으로 표기하지 않는다. `eol.exact_crossing_known=false`와 구간 양끝을 함께 기록한다. `rul_from_100_observation_EFC` 역시 관측 상한에 대한 값으로, 정확한 단일 정답이라고 해석하지 않는다.

상한·실패로 끝난 결과를 SOH 80% 수명 종료 정답으로 바꾸지 않는다. 장기 수명 정답은 별도 통계 처리나 추가 계산이 필요할 수 있다.

## 저장과 실패 복구

관측값은 모델 조각이 끝날 때마다 Parquet writer에 쓰며 전체 해 이력을 RAM에 쌓지 않는다. 주기 완료 또는 협조적 중단 시 writer를 닫고 `segment_*.parquet`를 확정한 뒤 마지막 물리 상태·단계·장부를 원자적으로 저장한다. 출력 경로는 잠금 파일로 중복 실행을 막는다.

강제 종료되면 확정되지 않은 `.partial`과 마지막 체크포인트 이후 구간이 남을 수 있다. 재개는 체크포인트가 인정한 파일 목록을 기준으로 자기 전용 출력 폴더의 미확정 구간만 정리한다. 원본 폴더는 수정하지 않는다. 강제 종료 전 소비한 시간도 `outcome.json`에 남겨 누적 시간 상한을 회피하지 않도록 한다.

핵심 파일은 `summary.json`(마지막 확정 상태), `outcome.json`(최종 판정 우선), `diagnostics.json`(복제 기준시험), `checkpoint.pkl`(재개), `lineage.json`(원본 계보), `segment_*.parquet`(연장 관측값)이다. 새 Parquet에는 원본 첫 100 EFC가 중복 저장되지 않으므로 학습 자료를 구성할 때 원본과 계보를 함께 사용해야 한다.

## 실행 예시

```bash
python simulation/run_lifetime.py \
  --cell 4 --current 3.2 --mesh-scale 4 \
  --efc 3000 --eol-soh 80 --max-wall-s 72000 \
  --rpt-every-efc 10 \
  --import-100efc-dir /var/lib/battery-capstone/results/main_100efc/current_3.2A \
  --output-dir /var/lib/battery-capstone/results/lifetime_cell4_3.2A
```

재개할 때는 같은 설정과 출력 폴더로 실행하고 `--import-100efc-dir` 대신 `--resume`를 사용한다. 같은 파일을 여러 프로세스에서 열지 않는다.

## 검증 범위

`simulation/verify_lifetime.py`는 짧은 기본 격자에서 기존 실행기의 0.05 EFC terminal 상태를 만들고, 새 출력 폴더에서 미완 방전을 이어가며 별도 프로세스의 중단·재개와 연속 계산을 대조한다. 원본 해시, Q0·EFC 장부, 첫 관측 단계, Parquet 재읽기·전하 적분, 기존 물리 제어기와의 차이를 확인한다. 추가로 잘못된 입력·원본 식별값 거부, 진단 종료 구간, 시간 중단 및 진단 callback 중단을 검사한다.

이 검증은 구현·재개 경로의 검사이다. ×4·×8의 100 EFC 정확도 검증이나 SOH 80% 장기 실험을 대신하지 않는다. 실제 AWS 100 EFC 원본을 새 실행기로 import하는 경로는 동일한 AWS 환경에서 추가 확인해야 한다.

## 부모·자식 종료 신호 검증

`simulation/verify_lifetime_signals.py`는 물리 계산 없이 종료 경로를 검사한다. Windows에서는 신호 handler·자식 전달·저장 대기·강제 종료 후 회수·자기 잠금 정리·다른 잠금 보존을 검증하였다. `outputs/verify_lifetime_signals_20261028/report.json`의 정책 검사 세 항목은 통과하였다. Windows의 외부 SIGTERM은 POSIX와 다르므로 실제 그룹 신호 검증을 완료했다고 쓰지 않았다. Linux에서는 부모 단독 SIGTERM, 부모·자식 프로세스 그룹 SIGTERM, 응답하지 않는 자식의 강제 종료 세 경로를 실제 프로세스로 확인할 수 있다.
